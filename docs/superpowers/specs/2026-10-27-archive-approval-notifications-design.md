## 2. 推荐入口和样稿范围

采用原顶栏一个铃铛，文案由“升级通知”改为“通知”，其中分“业务消息”和“升级通知”。原升级通知完整复用 `release-center/ReleaseCenter.vue`；“关于PMS”保持独立原入口。

备选为保留原铃铛、把业务通知放进用户菜单，影响更小但用户要从两个位置找通知。推荐统一入口，以减少寻找审批待办的步骤。

业务消息默认按最新事件排序，提供“全部／未读”切换、刷新和标准分页。列表只显示项目、事件、时间、未读状态；详情显示提交人/处理人、当前审批状态、必要结果，以及“查看申请”“标为已读”。标为已读不会完成审批。审批操作继续在原档案变更页面执行，通知里不再建一套审批表单。

进入通知窗口、页面重新获得焦点、审批操作完成时刷新；页面可见时每60秒更新未读数。切换用户或退出立即清空个人缓存。单个频道读取失败不会清空另一个频道，读取失败不显示成“0条”。不新增推送服务器或消息中间件。

先提供独立交互样稿，经用户确认后集成顶栏和正式通知模块。样稿复用PMS主题、Noto Sans SC和现有控件，覆盖：

| 状态 | 应有表现 |
|---|---|
| 正常、悬停、键盘焦点 | 当前消息清晰、点击区域明确、Tab/Enter/Escape可用 |
| 待审批、已通过、已退回、已撤回 | 状态与实际申请一致；已处理消息不提供处理动作 |
| 空、加载、请求失败 | 分别显示真实原因；失败可重试读取 |
| 无权或人员关系失效 | 通用不可访问提示，不显示项目或字段差异；不自动转发新审批人 |
| 只读、禁用、提交中 | 意见及按钮遵循原审批页和统一表单状态 |
| 邮件失败、等待配置、结果未知 | 普通用户流程不被技术信息占据；有权人员按需展开投递信息 |
| 三个现有主题、窄窗口、Mac/Windows | 使用同一字体与主题尺寸；真实Windows视觉证据不足时明确标注 |

## 3. 数据和事务

沿用已存在的发布通知模式，新增两张小表：`pms_business_notice`（个人事件及已读记录）和 `pms_business_notice_mail`（该通知的投递状态）。首批只支持档案变更审批，不建设可配置工作流。

个人事件的唯一约束包含申请ID、事件、申请版本和收件人ID；每条通知最多一条邮件记录。提交/通过/退回的业务变更、操作日志、通知和邮件排队在同一数据库事务中提交；任何一项写入失败整笔回滚。现有提交标识及决策幂等返回不再生成第二条通知。

通过、退回、撤回后原待办按当前申请状态展示为已处理或已撤回。尚未投递的旧待审批邮件在发送前核对当前状态；已经处理则停止投递旧待办。已被SMTP接受的邮件无法撤回。

数据库版本由当前 `2026-10-21-archive-policy-01` 升为 `2026-10-27-archive-notice-01`。限定升级脚本创建新增表、索引和权限节点，校验前置版本、结构及幂等性。生产启动仍只检查版本，不能自动建表或升级。开发只用临时SQLite数据库与SQL Server语法/迁移契约；真实MSSQL隔离验证及生产升级另批。

## 4. 权限与内容边界

个人接口先验证当前有效用户，只查询其本人通知，再复用现有档案查看权限、人员/部门和产品线范围。申请详情还必须满足原提交人或审批人关系。新增按申请ID定位接口遵循相同规则，不能仅凭链接ID访问。

待办投递前检查原审批人当前仍具备编辑权限、当前审批人资格和单据数据范围；结果投递前检查原提交人当前具备查看权限和数据范围。撤权、停用或人员关系变化时停止敏感内容投递；不补授权、不换收件人。读取列表、详情、未读数、标为已读时亦按当前权限过滤。

新增两个独立权限节点：`project:archive:notification:manage`（查看数据范围内投递状态）和 `project:archive:notification:retry`（受控重试）。不自动赋予现有角色，也不因角色名为admin而放行。管理接口须同时有档案查看权限及单据数据范围；重试再要求retry权限。开发夹具可建立虚构角色测试，不调整真实账户。

邮件仅包含项目编号/名称、事件、发生时间和PMS查看入口；退回意见在有权访问的申请详情中查看，不附整份字段差异、凭据或令牌。实际PMS链接只用已有可信配置，禁止消费请求Host拼接投递链接；若没有可复用的地址配置，邮件提供页面路径指引，不新增未批准外链。

## 5. 邮件和失败处理

复用 `feedback_mail.configuration/send_mail` 的SMTP配置、传输校验和凭据解密；使用本模块独立队列及现有线程式worker模式，提交成功后异步发送。新worker提供独立启停设置，本机验证只接模拟发信函数。

状态沿用待投递、等待配置、投递中、服务器已接受、失败、结果未知，并增加因权限或过期待办停止投递的状态。无邮箱及明确拒绝保留可定位原因；配置关闭保留队列；邮件失败不撤销已完成审批。数据库中的“服务器已接受”与站内已读分开记录。

用条件更新领取任务，两个worker不能同时领取同一条；发送进程中断的过期领取记录转“结果未知”。只有确定的临时SMTP拒绝可自动重试，最多3次；超时/连接中断等结果不确定情况不自动重发。固定Message-ID用于追踪，不承诺邮件严格只到达一次。

人工重试需要权限、原因；结果未知还要求确认已核查未收到。重试同一条投递记录，不再次生成通知。重试时重新检查用户、权限及当前业务状态。已接受或投递中的邮件不能重发。已读、邮件投递和重试都接统一操作日志并脱敏。
