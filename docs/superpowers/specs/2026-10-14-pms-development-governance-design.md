## 二、权限标准的结构

业务动作的允许条件为：功能权限、产品线范围、该业务适用的人员／部门范围、字段规则、单据状态和业务资格均满足。组织级ERP报表使用第一节确认的范围规则。

沿用现有运行时授权机制：按数据库中当前有效用户、角色和权限计算；不按角色名称设置全权旁路。`business:data:all`是可撤销的数据范围授权，不自动授予查看、编辑、删除、审批、同步或导出权限，也不替代档案负责人等业务资格。

产品线权限覆盖列表、详情、统计、查询候选、引用、关联单据、导出、下载和单据日志。单条接口不能仅依赖列表已过滤；修改归属时还需校验目标范围。缺少必要归属或授权时默认拒绝，全量访问必须走明确获授的规则。

现有服务继续作为基础：

- `backend/app/services/authorization.py`：登录用户与有效权限上下文。
- `backend/app/services/product_line_scope.py`：产品线授权与单条检查。
- `backend/app/services/business_data_scope.py`：全部业务数据授权语义。
- 项目／档案／ERP组织等资源通过各自适配器，把同一授权上下文转为查询条件和动作校验。

### 权限实施必须落实的技术细则

1. 建立业务模块登记，记录资源实体、产品线归属来源、人员范围策略、动作权限、说明键和日志关联。新业务接口必须声明适用规则。
2. 普通业务调用必须传入授权上下文；系统任务采用显式执行身份，缺少上下文不能默认得到全量数据。
3. 导出、同步等后台任务在执行前重新检查有效授权；正在进行或已经送达外部系统的操作按真实结果核查，不宣称撤权已撤回外部写入。
4. 系统管理、问题提报、通知等支持模块分别登记访问规则；涉及业务实体的链接、附件和内容必须再次检查实体权限。支持模块按第十节已确认政策执行，不从当前没有产品线字段推断为任意业务数据均可跨范围访问。

前三项是已确认统一授权原则的实施约束，不重新向用户询问底层函数或适配器选型；各批接口影响、回退及验证仍在具体实施计划中明确。

## 四、新页面开发标准（已确认）

本节开发准入标准已于2026-10-14获用户确认。既有字体、颜色、控件尺寸、查询规则、权限及日志约束继续按项目规范执行，无需重新选型。标准确认不等于旧页面已经完成迁移。

### 所有新增功能页的基本要求

- 登记页面、业务实体、动作权限及适用的数据范围；后端承担最终授权。
- 提供统一说明入口，内容覆盖真实操作、字段、保存、权限、计算、导出及通知规则。
- 复用全局视觉令牌和对应页面容器；提供加载、空数据、失败和重试反馈。
- 存在业务写入时接入统一日志；有引用字段时维护来源及只读规则。
- 字段和枚举通过统一目录／注册表维护，不在各页面重复定义同一套选项。

### 按页面类型使用标准容器

| 页面类型 | 标准组成 |
| --- | --- |
| 业务及管理列表 | 标准查询工作区、业务工具栏、数据区、列设置和分页；按document模式在依赖与必输条件就绪后自动首查。 |
| 报表 | 标准查询、汇总／明细、必要下钻和导出；按report模式进入待查询，保留已确认的联动例外。 |
| 新增／编辑表单 | 已确认的抽屉布局、统一字段控件、固定头部与底部、内容滚动；保存和关闭有明确状态。 |
| 主从页面 | 详情随已选择记录切换，使用共享草稿确认与异步竞争保护。 |
| 高频维护 | 使用统一表格编辑或详情行内编辑，保留自动保存及成功／失败反馈。 |

业务单据和报表的导出继续遵守现有独立权限与范围规则；系统管理不因本规范新增导出。导入、附件、审批、同步按业务需要接入，不要求所有表单提供同样的业务按钮。

### 优先补齐的共享模块

1. 业务模块登记与权限范围适配。
2. 表单会话与保存控制：原值、草稿、关闭确认、重复提交、错误定位、失败保留和并发冲突。
3. 页面数据状态与过期响应控制：待查询、加载、空结果、错误、重试。
4. 列偏好持久化：账号和页面键、失效字段清理、版本迁移。
5. 字段元数据适配：显示、可编辑、必输、只读原因及后端错误映射到统一控件。
6. 单据操作记录与版本通知中心。

这些能力保持独立职责，通过小型适配接入业务页，不把普通抽屉、详情行内和表格编辑合并成一个巨型表单。

### 新页面验收要求

验证目标业务流程、越权拒绝、日志准确性、说明一致性以及适用的保存／导出行为；共享UI验证显示、悬停、编辑、焦点、错误、禁用、只读、加载及Windows／macOS和OA窗口适配。项目已有必需契约和构建命令继续执行。旧页面按登记清单分批迁移，不随新标准一次替换全系统。

## 五、日志实施设计

使用同一事件底账，通过不同接口和字段输出服务管理员审计与单据操作记录。普通业务接口先校验单据当前访问权限，再读取关联事件，不授予用户全局日志权限。日志中字段差异须再次应用字段可见性及脱敏，隐藏字段不能从原值或新值泄露。

建议复用统一日志服务，补齐主单、子记录、审批、批次和任务之间的稳定关联。记录操作人、时间、来源、动作、真实结果和必要的前后值；关联删除不级联清除日志。

成功变更以数据库提交为准，业务值与成功日志同事务保存。自动保存按实际提交记账，无变化不生成业务修改记录；显示层可以合并连续事件，底账保留。同步区分排队、执行、成功、失败、待核查，不将超时或未知结果冒充确定失败。

业务用户看到操作者、时间、业务摘要、结果和有权查看的中文字段差异；IP、内部请求信息、技术异常及不允许查看的字段留在受控的管理员界面。主从切换沿用共享保护，防止旧单据日志响应覆盖新单据。

### 日志覆盖治理清单

本次代码审查发现的治理项包括：SSO自动开户／姓名变更缺少对应快照；部分后台过程只存在任务记录；后台导出失败与日志结果字段不一致；项目级联删除未保留完整任务快照；自由文本摘要和异常未统一脱敏。这些应在实施版本重新核对并逐项修复，不按当前文件存在日志调用就判定覆盖完整。

### 日志策略与工程边界

- 保存／清理、失败及越权审计、管理员导出按第十节已确认首期政策执行。
- 成功日志与业务变更同事务；失败审计在业务事务回滚后使用独立短事务，不提交失败业务数据。日志采集异常须可被运维发现，不能用审计写入重试重复执行业务动作。具体限流参数由工程测试确定并记录，不向普通用户增加设置。
- 新事件保存必要的历史字段名、枚举名、引用名称快照，避免资料改名后历史含义变化；仍按当前字段权限裁剪。历史日志缺少的值不得伪造补齐，兼容显示已有信息。
- 运维脚本按受控维护规则留痕；直接数据库写入的自动追踪不在当前应用日志范围，若需数据库审计再另行立项。

## 六、版本和发布设计

发布流程为：开发完成、集成验收、锁定发布内容、同步更新说明、制作固定版本包、发布与现场验证、创建用户通知。正式版本号对应唯一代码提交及文件清单，数据库结构版本独立记录。发布状态不由前端写死，开发、测试、正式环境返回各自实际运行信息。
