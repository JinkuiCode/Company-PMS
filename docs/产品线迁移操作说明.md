## 页面配置顺序

1. 升级发布后，使用具有配置权限的账号进入「系统管理 → 产品线管理」（`/system/product-line`）。点击「新增产品线」，搜索并选择金蝶组织，填写希望显示的产品线名称后保存。一个产品线绑定一个组织，组织绑定创建后不可更改；显示名、排序、启停可以维护。
2. 先创建上述两条历史归属所需的产品线。显示名称由用户决定，迁移按组织内码查找真实 PMS 产品线编号，不依赖显示名。
3. 进入「系统管理 → 角色管理」，编辑角色，在「授权产品线」勾选后保存。各角色授权由用户操作，迁移清单的 `roles` 使用空数组，不代用户批量分配。管理员也不自动获得全部产品线；未勾选时看不到项目数据，多角色取并集。
4. 对已确认的 Bench、Single 历史档案生成目标库清单并执行迁移。配置或授权修改后重新取快照，避免使用过期清单。
5. 验收项目档案、项目进度和采购报表；新建档案的产品线仅展示当前账号有权且启用的值。缺少归属的历史档案不会因管理员身份绕过限制。

配置入口已发布至服务器。产品线管理的菜单权限与项目数据的产品线授权相互独立，配置账号可以先建产品线再分配数据授权。部署验证时产品线和角色产品线关联表均为空，940 条档案原有业务内容不变，新归属未填写；配置及迁移前项目列表为空是拒绝未授权数据的结果，不表示档案删除。

服务器数据库备份、结构升级和正式应用窗口仍需单独确认。不重启 SQL Server、OA 或服务器。

## 只读检查

在已经配置正确数据库连接的专用终端，从 `backend` 目录运行：

```bash
python scripts/migrate_product_line_assignments.py
```

默认不写数据库，也不调用初始化。结果只放在 PMS 内的 `.runtime/product-line-migration/`，不放到服务器 C 盘根目录。
同时生成 JSON 快照和中文 Markdown 清单，分类为：未归属档案、项目编码冲突、进度缺少有效档案引用、角色需明确产品线授权。
结构尚未升级的数据库也可只读检查，缺少的新归属字段按“未设置”列出。
目前工具不自动扫描采购活动生成“唯一候选”或“多个组织冲突”；这些业务证据仍须另外只读核对，不能把没有候选当作已经确认归属。

## 确认清单格式

### 按已确认映射只读生成

页面创建好目标产品线后，先核对目标数据库中 Bench、Single 对应的旧枚举存储值，再准备映射 JSON 数组。每项仅包含两个整数：`legacy_product_line_id`（核对后的旧枚举值）和 `organization_id`（Bench 为 200292、Single 为 4146325）。不要把这两个组织内码当成旧枚举值，也不要采用其他数据库的旧编号。

```bash
python scripts/migrate_product_line_assignments.py --prepare-mapping 已核对旧值映射.json
```

该命令只读：按组织内码读取用户创建的真实产品线编号，仅选择尚未归属且旧值明确匹配的档案，生成带当前快照指纹的 `.plan.json`。角色清单固定为空，不更改页面配置。输出报告另列 `unmatched_archives`，保留空值或未知旧值供人工核对。

目标产品线尚未创建或已禁用、旧值重复、数据库版本不符、项目编码冲突等情况不会产生可执行清单；没有匹配档案也不会产生空批次。生成清单不等于已经迁移，实际应用仍按下节独立执行。`--prepare-mapping` 不允许与 `--plan` 或 `--apply` 同时使用。

### 完整清单结构

以下仅为格式示例，不是实际组织或角色分配：

```json
{
  "source_revision": "2026-09-21-02",
  "source_fingerprint": "替换为目标数据库结构升级后重新检查得到的64位指纹",
  "lines": [
    {"key": "kingdee:100", "product_line_id": 1, "organization_id": 100}
  ],
  "archives": [
    {"archive_id": 1, "project_code": "示例项目编码", "legacy_product_line_id": null,
     "target_product_line_key": "kingdee:100"}
  ],
  "roles": [
    {"role_id": 1, "product_line_keys": ["kingdee:100"]}
  ]
}
```

- `lines` 必须引用已经通过组织候选核对并创建的 PMS 产品线；工具不创建产品线、不改绑定、不重命名。
- `archives` 仅能给尚未归属的档案填入新归属；已有归属不能被本工具覆盖。
- `roles` 对列出的角色采用明确替换；没有列出的角色不变。本批用户已选择通过页面自行授权，实际迁移填写 `"roles": []`，不要套用上方格式示例的角色分配。
- 数据库升级、创建产品线后必须重新导出快照。快照之后的相关修改会令清单失效，禁止手工伪造指纹绕过。

## 校验与应用

```bash
python scripts/migrate_product_line_assignments.py --plan 已确认清单.json
```

不带 `--apply` 只校验，不写入。正式应用必须另外获得明确批准，在维护期暂停 PMS 写入和同步工作进程，使用独立维护连接执行：

```bash
python scripts/migrate_product_line_assignments.py --plan 已确认清单.json --apply --operator-id 实际操作人ID
```

操作人在 PMS 中必须为有效用户，并拥有 `system:product-line:migrate` 权限。无管理员角色旁路。
工具在一个事务内锁定和复核来源、写档案归属与角色关系，并写一条完整操作日志。任何校验或写入失败整批回滚。
清单摘要作为审计批次标识；相同清单重复应用不再写入，因此不会补回后来人工撤销的授权。不要删除迁移批次日志。
如果提交之后结果文件写出失败，先检查批次审计；重复运行同一清单仍不会重新授权。

## 发布验收

- 前后端必须同批切换：API `product_line_id` 代表新组织主数据；数据库旧 `product_line_id` 仍仅保留历史枚举。
- 升级前的未绑定同步任务不能直接继续发送；核对归属后由管理员处理失败/待核查任务。迁移本身不会向金蝶发送请求。
- 分别使用单组织、多组织、无组织授权用户验收档案、进度、报表详情和导出；同一登录状态撤权后立即拒绝。
- SQL Server 实际锁行为和升级回滚仍需目标环境验收，本地 SQLite 通过不等于生产验证。
- 回滚须同时考虑程序、结构及授权数据，不得直接恢复旧宽权限程序继续运行。
