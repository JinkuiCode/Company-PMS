# 列表查询、分页与显示修复

## 范围与边界

- 用户已批准：档案真实分页、加载优化、列内文字截断，以及其他页面同类问题修复；特别要求保留查询与保存后的联动。
- 本批仅开发机实施、验证。没有部署服务器，没有修改正式期初档案、数据库结构、权限规则或金蝶映射。
- 沿用现有功能分支。期初导入批次的文档改动保留，不混为本批代码。

## 查询联动

1. 项目档案的关键词、启用状态、产品类别、自定义条件、排序共同组成一次服务端查询。SQL 先执行权限范围、筛选和稳定排序，然后计算总数、取当前页。
2. 修改条件回第一页；翻页保持条件；修改每页数量回第一页；同一批条件恢复由监听器合并请求。查询变化清空勾选，防止对隐藏的上一页记录执行批量操作。
3. 当前系统保存的是个人列布局（含排序），并没有独立的命名查询方案。本批没有凭空增加查询方案功能。先恢复已有列排序再查询，避免先显示默认结果、再被旧布局改变顺序。
4. 保存档案仍按原条件和页码刷新；记录不再符合条件时从结果中消失，总数同步变化，但详情抽屉按 ID 获取已保存内容。末页减少后自动回到最后有效页。
5. 列表请求带序号，过期响应不能覆盖新条件。加载状态与空结果区分；档案加载失败显示重试入口。

## 同类页面检查

| 页面 | 检查结果与处理 |
| --- | --- |
| 项目档案 | 修复固定取 1000 条、未真正分页、逐行查人员、跨列文字溢出 |
| 项目进度 | 保留现有动态字段客户端筛选；一次读取权限范围内完整结果，避免分批查询时记录移动导致漏项，不再截断在 1000 条；AG Grid 对完整结果排序后分页，而不是只排序当前切片 |
| 操作日志 | 将自定义筛选从当前页移到 SQL 分页前；同步总数、页码及过期请求保护 |
| 数据字典 | 已有真实服务端分页；补充过期请求保护和失败时 loading 收尾 |
| 用户管理 | 已有真实服务端分页；补充过期请求保护和失败时 loading 收尾 |
| 角色、枚举、字段规则、任务页 | 未使用档案的固定 1000 条伪分页路径；不改变现有无分页/主从/任务交互。AG Grid 文本列复用共享截断修复 |

项目进度当前仍需完整数据支持现有计算字段/动态筛选，不能把它描述为服务端筛选优化；数据量很大时仍有全量加载成本。本批解决截断及排序分页一致性，不重新设计其动态字段查询引擎。

## 验证

- 后端新增 `archive_pagination_contract.py`：1040 条本地 SQLite 档案；15 条一页；人员关联存在时仅 6 次 SQL；本次测量约 4ms。此结果不是正式 MSSQL 网络环境的耗时承诺。
- 验证分页前筛选/排序、客户搜索、通配符按文字处理、人员名称、日期边界、范围权限、未知字段拒绝；操作日志筛选能找到原先不在第一页的记录。
- Edge 无头浏览器使用隔离模拟接口：940 条档案，默认 15 条、翻页、每页数量、条件联动、旧请求覆盖防护、错误重试、排序保存及刷新恢复、自定义筛选、保存后离开筛选结果的抽屉刷新、末页回退。
- 项目进度浏览器测试使用 2040 条记录，验证完整总数、第二页、跨全部记录排序和搜索第 1000 条以后的记录。
- 1366×768、1600×900 截图检查通过。项目名称列宽 190px，值区域 168px，`ellipsis` 生效；客户内容不再被遮盖。
- 全部后端契约、前端契约及生产构建通过。构建仍有既有大包警告；本批不做打包架构改造。

验收时在开发机双击 `start-pms.command`，访问 `http://127.0.0.1:5174/project/archive`。自动化验证使用临时开发服务，不代表结束后服务常驻。正式服务器仍待用户验收后部署。
